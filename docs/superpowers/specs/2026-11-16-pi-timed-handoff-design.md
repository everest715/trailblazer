# Pi 定时 Handoff 设计

## 意图

在现有 `/new`、`/resume`、正常退出保存之外，为长时间运行的 pi 会话增加周期性 `HANDOFF.md` 更新，降低 KV cache 失效或异常退出后丢失近期工作的风险。

## 目标与约束

- 每个会话启动 300,000ms（5 分钟）周期的检查。
- 仅当 `ctx.getContextUsage()?.tokens > 100000` 时允许定时保存；使用量不可读时跳过。
- 仅当当前会话叶节点不同于上次成功摘要的叶节点时生成，空闲会话不调用模型。
- 100k 阈值只限制定时保存；`/new`、`/resume` 和正常退出仍沿用原保存逻辑。
- 空会话、空摘要或生成失败不得覆盖旧文件。
- 定时器必须在 `session_start` 建立，在 `session_shutdown` 幂等清理，不能阻止进程退出。

## 方案比较

- **每 5 分钟强制保存**：行为直接，但无变化时重复调用模型，费用高，不采用。
- **每 5 分钟检查，超过 100k 且有变化才保存（选定）**：兼顾定期更新和调用成本。
- **连续空闲 5 分钟后保存**：不保证活跃会话按固定周期更新，不采用。

## 实现

- `core.ts` 增加可独立测试的定时调度与阈值判断。
- 调度器支持启动、停止、重复启动保护，并共享进行中的保存 Promise，防止定时器和生命周期事件重入。
- `index.ts` 在每次 `session_start` 创建调度器，在 shutdown 停止；定时器调用 `unref()`。
- 摘要开始时记录会话叶节点。只有成功写入后才把它标记为已保存；生成期间追加的新内容仍保留下次保存。
- 定时保存和现有切换/退出保存共用同一生成与防重入路径。

## 验证

- Node `node:test` 使用 fake timers 验证 5 分钟触发、停止清理和重复启动。
- 验证阈值边界 `100000` 不触发、`100001` 触发、未知使用量跳过、无新内容跳过。
- 验证慢保存期间不会发生第二次并发调用。
- 运行 `node --check`、全部扩展单元测试及一次短间隔真实 pi 冒烟测试。
